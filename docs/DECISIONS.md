## Post-Phase-4 — user decisions (2026-10-31)

- **D-046** — Model artifacts: **regenerate, do not commit.** `ml/models/models.joblib` is 23.5 MB and `anomaly_model.joblib` is 3.4 MB; both are reproducible from the fixed seed (`ml/generate_data.py`), and `ml/models/` is already gitignored. Committing 27 MB of regenerable binaries would bloat the repo and invite code/model drift. The committed evidence is `ml/reports/metrics.json` (textual, measured). Documented in README §6.
- **D-047** — Login lockout (closes OQ-12): 5 consecutive failures → 15-minute lock, counter reset on success, identical generic 401 for unknown/wrong-password/locked (no disclosure of account existence or lock state), Super Admin unlock via the new `users.unlock` permission, and **only** lock/unlock audited. Individual failed attempts are deliberately not written, because auditing each guess is both ledger noise and a log-flooding vector. Migration `008_login_lockout.sql` adds `users.failed_login_attempts` and `users.locked_until`. A `demo:reset` script clears locks between demonstrations.
- **D-048** — Super Admin unlock is its own permission (`users.unlock`) rather than reusing `users.suspend`: clearing a temporary lock is not a sanctions decision, and conflating them would let a Moderator reverse a security control they cannot apply.
- **D-049** — `bootstrap.mjs` now refuses to overwrite an existing `server/.env`, and checks that **before** any database work. Order matters: the script rotates the role passwords, so refusing afterwards would leave the database and `.env` inconsistent and lock the operator out. `--force` is the explicit override; generated secrets are never printed.
- **D-050** — Production seeding reads `SEED_VIEWER_PASSWORD`, `SEED_MODERATOR_PASSWORD`, `SEED_SUPERADMIN_PASSWORD` and refuses to run with `NODE_ENV=production` unless all three are set, non-demo and at least 12 characters. Credentials are not echoed in production. Rationale: a demo password reaching a deployed system is a live vulnerability, so the tooling refuses rather than warns.
- **D-051** — `npm run dev:all` (`scripts/dev-all.mjs`) starts API + frontend + model service. It defines the model port once and derives both the uvicorn argument and `MODEL_SERVICE_URL` from it, so the URL cannot point at a port the service is not on. The model service is spawned with `shell: false` (a real executable): with a shell, the space in the workspace path `GLM Projects` is passed to cmd.exe unquoted and the spawn fails — observed and fixed during testing.
- **D-052** — The model-service environment variable is named **`MODEL_SERVICE_URL`** (not `ML_SERVICE_URL`), consistently across `server/src/services/modelClient.ts`, both env templates, `dev-all.mjs` and the README. No rename was needed; recorded because the two names were easy to conflate.
- **D-053** — OQ-11 closed as **won't do**: MFA, SSO/OIDC/SAML, passwordless login, biometrics and passkeys/WebAuthn remain out of scope per Chapter 5 §3.6.2 (email + password with JWT role claims). Passkeys in particular (`SEC-AUTH-006`, `FR-IAM-029`) are recorded under Future Work in the Phase 5 draft rather than dropped silently.
- **D-054** — Test-suite architecture changed so a fresh clone reports **skipped**, not failing. Six database-backed suites imported `src/db/pool` (and two imported modules that transitively did) at module load; `db/pool` validates the environment and throws without `DATABASE_URL`, so removing `server/.env` turned six suites into import-time failures. Three extractions fixed this: `config/lockout.ts` (policy constants with no pool dependency), `lib/csv.ts` (the pure CSV formatter, moved out of the route module), and `tests/helpers/db.ts` (`hasDb` + `createPool` called from `beforeAll`). Result verified in both states: **with** a database 81/81 pass; **without** one, 6 suites skip and the 7 pure tests still pass, 0 failures.
- **D-055** — The disposable PostgreSQL cluster (`server/.pgdata`, port 5433) was removed at the operator's instruction, together with the `server/.env` that pointed at it. The stale `.env` had to go as well: `bootstrap` now refuses to overwrite an existing `.env`, so leaving it would have blocked the operator's own Path A bootstrap. Both are gitignored and untracked (verified: 0 tracked files). A throwaway cluster outside the repository was used once to verify the test suite after the D-054 refactor, then removed.
- **D-056** — Local-VM deployment path documented in **`docs/DEPLOY_VIRTUALBOX.md`**, because the instructions supplied were written for Azure and two of them do not translate to Oracle VirtualBox. (a) A "DNS name label" has no VirtualBox equivalent: a NAT VM has no public address, so **Let's Encrypt cannot validate it**; the document states this plainly and offers four options, recommending local HTTP for the demo. (b) "Allow only ports 22/80/443" becomes `ufw` on the guest plus VirtualBox NAT port forwarding, since 3000 and 8000 bind to loopback and are never published. The document also corrects the claim that the model service "refuses to start" on a scikit-learn mismatch: it **degrades** instead — `/health` reports `degraded`, `/predict` returns 503, and the console shows "Suggestion unavailable" (D-055 of the ML design). The check is therefore `/health`, not a crash.
- **D-057** — **Two defects found in `deploy/smoke-test.sh` and fixed** while validating the local-VM path, both of which would have produced misleading results on the actual deployment. (a) Check 5 assumed an unexposed model service returns 404, but the Nginx config's SPA fallback (`try_files $uri $uri/ /index.html`) returns **200 with index.html**, so a *correct* deployment reported "model service appears publicly reachable". (b) The first fix then produced a **false negative**: it used GET, while `/predict` is POST-only, so an exposed service answered 405 with no model body and the check passed. The check now POSTs a minimal valid payload and fails on either a `model_version` body or a FastAPI `"detail"` error envelope. Verified both directions: **13 passed / 0 failed / 0 skipped** against an Nginx-style origin, and a deliberate **FAIL** against a proxy that leaks `/predict`. A check that cannot fail is worse than no check.
- **D-058** — Observed during validation: the operator had already run Path A against their own PostgreSQL on port 5432, and `bootstrap` correctly **refused to overwrite** the resulting `server/.env` (the D-049 guard working in practice). Migration and seed were then run against that database; both are idempotent, and the sample data was re-seeded after the smoke test to restore the escalated flag.
- **D-059** — `MODEL_TIMEOUT_MS` raised from 800 to 3000 ms. Measured on the development machine: the first node→model connection takes ~2.4 s, warm scikit-learn calls take ~220 ms, and pooled fetches run 210–250 ms. At 800 ms the client was aborting real predictions (`AbortError` → "Suggestion unavailable") even with a healthy, loaded model. 3000 ms still fails fast: a down service fails instantly on connect, a stuck one within 3 s, and the queue renders regardless. Updated in `modelClient.ts`, `server/.env.example`, `deploy/.env.production.example`, `scripts/dev-all.mjs` and the README. Verified end to end after the change: a live suggestion returns `available: true, severity: High, action: reject, confidence: 0.481`.
