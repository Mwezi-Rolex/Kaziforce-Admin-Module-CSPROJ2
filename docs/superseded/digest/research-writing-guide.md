## Build process the guide mandates (Sprint Phase)

6. Sprint I: configured development environment; clean, professionally organised codebase with clear folder structure and setup/run instructions; Git version control with meaningful commits and no secrets in the repository; prepared resources; appropriate automation for setup, data preparation and testing; earlier chapters corrected so Chapter 4 matches the system being built.
7. Sprint II: sprint tasks linked to objectives with done/in-progress/blocked status; a working core workflow demonstrated from input through processing to output — "screens, mock-ups or isolated components alone do not demonstrate completion of the core workflow"; interface, application logic, database and APIs integrated with data moving correctly between them; initial testing covering expected behaviour, invalid inputs and failure conditions, recording test performed, expected result, actual result and corrective action; initial evaluation evidence — for software projects, core user tasks, data validation and access controls; updated Chapter 5 with screenshots, outputs and test records; Chapter 4 diagrams updated where design changed; up-to-date repository with setup instructions, reproducible version, documented known limitations and outstanding defects; repeatable tests through GitHub Actions with results retained alongside the commit.
8. Sprint III: completed functionality linked to objectives with a traceability record connecting each objective or requirement to its implemented component, test or evaluation, result and supporting evidence; a coherent system organised around real user tasks with suitable navigation, readable interfaces, consistent interactions, appropriate access controls and helpful feedback; a working operational release accessible over HTTPS with the actual backend and database connected; completed testing and evaluation including usability and failure scenarios, saved evidence, correction and retesting of important defects, and a discussion of limitations; a complete report and reproducible handover covering Chapters 5 and 6, corrections to earlier chapters, the final release, setup and operating instructions, and demonstration materials.
9. Module rule: build and verify one module at a time. Define the module's user role, task, inputs, rules, stored data, outputs and dependencies and its completion criteria; sketch entry point, fields, actions and outcome; specify empty, loading, success, validation-error, service-error and permission-denied states; implement a complete vertical slice with real persistence; test valid and invalid inputs, boundaries, permissions, duplicate submissions, interruption and dependency failures; review with a representative user; integrate and regress.
10. Architecture rule: keep presentation, application rules, data access and service integration separated, and enforce business rules and permissions on the server as well as in the interface.
11. "A small, well-structured application can be sufficient; extra services should solve a demonstrated need." Visual polish supports task completion; "clear hierarchy, readable content and predictable interactions matter more than adding decorative dashboards or numerous screens"; show an honest empty state instead of fabricated totals or charts.
12. HCI checks: consistent visual language; distinguish destructive actions and confirm when justified; label fields, validate on client and server, place corrections near the affected field and preserve valid entries; replace generic "Something went wrong" with actionable text; make processing, completed, saved, failed and cancelled states visible; prevent unintended repeat submissions; support cancel/back/correction/undo; keyboard operability, visible focus, readable contrast, no colour-only status signalling.
13. AI-use rule: "Record material AI assistance and follow applicable institutional disclosure requirements"; the author remains responsible for the design, behaviour and research conclusions; AI explanations are hypotheses to be checked, and no unverified AI statement or invented citation may become a finding.
14. Diagram rule: update Chapter 4 architecture, data, interaction and state diagrams to match the implementation; "the diagram, code, interface and report should describe the same system."
15. W3C WAI references to apply: form labels and instructions, success/error/status notifications, page structure and navigation.
